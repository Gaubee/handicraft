## 0. 决策框架（framing）

**决策句**：为贴钻工作台裁定——(a) 新增第四模块「素材库」的虚拟文件系统模型与三模块图片管理重构方式；(b) 转化工作台布局的完全重设计方案。截止：随两个 OpenSpec change 进入实现。

**问题框定**：

- 素材侧：设计师的图片资产散落在四处互不知情——实验室参考图（会话内 objectURL，刷新即失）、生成结果（IndexedDB 扁平 `images` store，key=taskId，只能靠画廊批次浏览）、工作台入图（handoff dataUrl 或本地重复上传）、案例图（public/presets 静态文件，无管理界面）。同一张图被二次上传、跨模块复用无门、删除即永久消失。Evidence: `lab.svelte.ts` L162（reference 为会话态）、`imageStore.ts`（扁平 `{id,blob,createdAt}` 无层级）、`studio.svelte.ts` L74-82（origin 仅 handoff|upload）、`effectRefs.ts`（preset 静态路径直引）。
- 工作台侧：上版三轮视觉迭代后 Owner 仍不满意，要求「完全设计」——判断根因不是视觉打磨不足，而是**结构性问题：画布是滚动物件而不是常驻舞台**（§3.3 诊断）。Evidence: `StudioView.svelte` L107-186（主区为滚动列，画布 `h-[45vh]` 嵌于其中）；Owner 原话「布局需要完全设计，重新设计这个界面的使用体验」。

**非目标**：

- 不做云同步/后端（无后端约束不变，全部 IndexedDB + localStorage）
- 不做素材级协作/分享
- 不改变工作台→手动编辑烘焙原则（冲突点单独标注，见 §6）
- 不动引擎（`$lib/engine` 零改动）

## 2. 设计任务一：素材库（虚拟文件系统）

### 2.1 定位与原则

**素材库 = 图片资产的唯一真源（canonical store）；各模块是它的消费者。**

四条原则（后续所有细节裁决的依据）：

1. **One Library**：「用户该去哪找一张图」只有一个答案。选图器（Dialog）是素材库在各模块内的投影，不是第二套管理界面。
2. **上传即入库（ingest-on-upload）**：任何入口上传的本地文件先落库（进入当前目录或来源目录），再建立引用。纯本地的临时图不再存在。
3. **资产不可变（asset immutability）**：图片内容永不修改，只有元数据（名称/位置/标签）可变。这条是「跨模块传 assetId 引用」安全性的基石，也是与手动编辑烘焙原则不冲突的原因（§6）。
4. **生产者自动归档**：生成结果、精修导出 PNG 自动入库到约定目录，用户零操作；目录结构用户可随后整理。

### 2.2 虚拟文件系统数据模型

#### 2.2.1 节点模型（`src/lib/persistence/assetStore.ts` 新建）

```ts
export type AssetNodeId = string // 'ast-' + crypto.randomUUID()

export type SystemFolderId = 'sys-cases' | 'sys-generated' | 'sys-uploads' | 'sys-exports' | 'sys-trash'

interface AssetNodeBase {
  id: AssetNodeId
  name: string            // 同父内唯一（§2.3）
  parentId: string | null // null = 根层；系统目录固定 parentId=null
  createdAt: number
  updatedAt: number
}

export interface AssetFolder extends AssetNodeBase {
  type: 'folder'
  system?: SystemFolderId // 系统目录：只读保护 + 固定语义
}

export type AssetSource = 'upload' | 'lab-generate' | 'edit-export' | 'preset' | 'migrated'

export interface AssetImage extends AssetNodeBase {
  type: 'image'
  refKind: 'blob' | 'external'
  blobKey?: string         // refKind='blob'：IndexedDB images store 的 key（复用，不搬数据）
  externalUrl?: string     // refKind='external'：静态资源直址（案例图，不入 IDB）
  mime: string
  width: number
  height: number
  bytes: number
  thumbKey?: string        // P1：独立缩略图 key；P0 网格直接渲染 blob（objectURL 缓存）
  source: AssetSource
  meta?: {
    runId?: string         // source='lab-generate'
    variantName?: string
    candidateIndex?: number
    prompt?: string        // 截断 200 字，搜索用（P1）
    originNote?: string    // 案例来源说明（preset）
  }
  trashedAt?: number       // 非空 = 在回收站
}

export type AssetNode = AssetFolder | AssetImage
```

要点：

- **path 是派生量**：由 parentId 链现算（面包屑/移动环检测用），不存储——重命名/移动永远不破坏引用（引用只认 id）。
- **blob 与节点分离**：`blobKey` 指向既有 `images` store 的记录。资产「文件名」与 blob key 解耦，改名零成本。
- **external 引用**：案例图（8 组真实案例，`public/presets/`）不复制进 IDB，节点直接指静态路径；随版本更新由代码 seed 同步（§2.4）。

#### 2.2.2 存储方案（IndexedDB v2）

现库 `rhinestone-studio` v1 仅 `images` store（`imageStore.ts` L6-8）。升级：

```
DB rhinestone-studio @ version 2
├─ images            （不动，继续当 blob 仓：{id, blob, createdAt}）
└─ assetNodes  新增  keyPath='id'
   ├─ index 'parentId'  （取子级：树渲染/网格列目录）
   ├─ index 'updatedAt' （最近使用排序）
   └─ index 'trashedAt' （回收站过滤）
```

- 节点元数据放 IndexedDB 而非 localStorage：任务 meta 已有三级配额降级先例（`taskStore.ts` L87-102），资产树只增不减，localStorage 必爆。
- localStorage 只存一个 flag：`rhinestone-studio:asset-migration-v2`（迁移幂等标记）。
- objectURL 生命周期：assetStore 维护模块级 `Map<blobKey, objectURL>` 缓存 + LRU 上限（P0 取 200 条，超限 revoke 最旧）——三模块共用一份，解决现在 lab/compare 各自建 URL 各自 revoke 的散乱。

#### 2.2.3 迁移策略（存量数据 → 素材库）

**原则：blob 一律不搬不复制（`images` store 原地复用），迁移只做「建节点 + 摆目录」。**

触发时机：应用启动 hydrate 时（`main.ts`/App 挂载后异步执行，不阻塞首屏），检查 flag 未置位则跑：

1. **seed 系统目录**：`sys-cases / sys-generated / sys-uploads / sys-exports / sys-trash`（不存在才建）。
2. **案例图入 `sys-cases`**：遍历 `EFFECT_REF_PRESETS`，为每条建 image 节点（`refKind:'external'`, `source:'preset'`, name=案例名，meta.originNote=sourceNote）。节点 id 固定 `ast-preset-<presetId>`（幂等跳过；版本更新时按 presetId upsert）。
3. **生成结果入 `sys-generated`**：读 localStorage 任务 meta（`loadTaskMetas()`）中 `status==='success' && imageStored` 的任务 → 建 image 节点（blobKey=taskId，meta 带 runId/variantName/candidateIndex）。**按 runId 分组建批次文件夹**（命名 `第 N 次生成 · MM-DD HH:mm`，N 沿用画廊批次序口径 `lab.svelte.ts getTaskGroups`）；`LEGACY_RUN_ID` 归 `更早` 文件夹。blob 缺失（imageMissing 同款口径）的节点照建，标 `missingBadge`（§2.6 状态矩阵）。
4. **效果参考上传入 `sys-uploads`**：扫 `images` store 中 `effectref-` 前缀 key 且 blob 存在的记录 → 建节点（name 取 key 尾段时间戳可读化 `参考图 MM-DD HH:mm`；无任务语义，source='migrated'）。**不再随变体替换删除**（行为变更 B-3，§2.5）。
5. 置 flag；全程 try/catch，任何一步失败下次重跑（所有步骤幂等：节点存在即跳过）。

回滚：无需回滚——迁移只增节点不动 blob；「素材库故障」最坏退化为 v1 行为（各模块仍可直接读 blob key）。

### 2.3 文件操作规则（状态矩阵）

| 操作 | 规则 | 反馈/恢复 |
|---|---|---|
| 新建文件夹 | 任意用户目录/根层；系统目录内禁止 | 即时出现在树与网格 |
| 重命名 | 同父内唯一：冲突自动后缀 ` (2)`；系统目录与 `sys-cases` 内条目禁改 | 行内编辑（网格/树均可发起）；Esc 取消 |
| 移动（P0 走「移动到…」对话框选目标；P1 拖拽） | ① 不可移入自身或后代（环检测：沿 parentId 链向上查）② 目标只接受文件夹 ③ `sys-cases` 条目与系统目录本身不可移动 ④ 移入回收站 = 删除（同一下文） | 移动仅改 parentId；引用零感知 |
| 删除 | **软删**：移入 `sys-trash`（trashedAt=now, parentId=sys-trash）。确认对话框列出将删除的「N 张图片 / M 个文件夹（含 K 项）」；系统目录不可删 | 回收站内可还原（P1 还原 UI；P0 数据结构已支持）与「清空回收站」 |
| 清空回收站 | **硬删** blob + 节点。被引用的资产跳过并明示：「3 张正被变体效果参考引用，已保留」（引用集扫描 §2.5） | 不可撤销，红色确认（点名破坏：`清空回收站（永久删除 17 项）`） |
| 拖拽上传/导入 | 外部文件拖入库界面 = 上传即入库（落当前目录）；树内拖拽移动 = P1 | 上传进度 toast |
| 导出下载 | 单图/多图下载原 blob；文件夹下载 = P2（zip） | — |

**回收站 vs 硬删的裁决**：P0 即软删。理由：软删实现上只是 parentId 指针 + 一个时间戳（比硬删的引用保护还简单）；图片资产误删代价高（生成图的 prompt 上下文不可再生）；成本几乎为零的保险没有理由推迟。（议题 5，附反对方向供 Codex 挑战。）

### 2.4 目录语义（seed 结构）

```
素材库
├─ 案例（系统·只读）      sys-cases     内置 8 组真实案例（原图+效果图对），随版本更新
├─ 生成结果              sys-generated 每次开始生成 = 一个批次文件夹（自动）
├─ 上传                  sys-uploads   手动上传默认落点（选图器内上传亦然）
├─ 精修导出              sys-exports   手动编辑导出 PNG 自动落点
├─ 回收站                sys-trash     软删内容
└─ （用户自建文件夹，任意层级）
```

- 生成批次文件夹在 `startRun()` 时预建（name：`MM-DD HH:mm · N 张`，N=usable 变体数×候选；与画廊组头时间一致）。任务成功建资产节点时挂入。
- 系统目录「只读」的准确语义：**目录本身不可删/改名/移动；`sys-generated/sys-uploads/sys-exports` 内条目可整理**（移入自建文件夹=合理收藏行为）；唯 `sys-cases` 条目完全只读（外部引用无 blob，删除无意义）。

### 2.5 三模块图片管理重构（需求 6 核心）

#### 统一选图器（AssetPickerDialog）

一个组件，三种调用形态：

```
┌─ 选择图片 ────────────────────────────────┐
│ 快捷: [最近][案例][生成结果][上传][全部]     │ ← 智能集合 chips（P0：最近/全部/三个来源目录）
│ 📁 生成结果 / 09-18 14-30 批次      [⌂][▴] │ ← 面包屑（⌂根 · ▴上级）
│ ┌────┐┌────┐┌────┐┌────┐┌────┐          │
│ │ ✓  ││    ││    ││    ││ 📁 │           │ ← 单选（默认）或指定 multi
│ │img ││img ││img ││img ││文件夹│          │
│ └────┘└────┘└────┘└────┘└────┘           │
│ …（objectURL 网格，hover 显示名称/尺寸）    │
├──────────────────────────────────────────┤
│ [⬆ 上传新图片]              [取消] [确定]  │
└──────────────────────────────────────────┘
```

- **双入口并存，但上传是入库的前置**：选图器内置「上传新图片」（落当前目录→自动选中）。各模块的原生 Dropzone/上传按钮保留（习惯路径不砍），但其 handler 改为「入库 → 选中」而非「仅会话持有」。
- `最近` 集合 = updatedAt 降序前 24 项（选图最高频动线是「刚生成/刚传的那张」）。
- 确定返回 `AssetImage`（含 blobKey/externalUrl），调用方经 `objectUrlForKey(blobKey)` 取展示 URL。

#### 实验室（LabView / lab.svelte.ts）

| 项 | 现状 | 重构后 |
|---|---|---|
| 参考原图 | Dropzone → 会话 objectURL，刷新丢失 | Dropzone 保留（上传→入库 `sys-uploads`→选中）+ 新增「从素材库选择」；reference 状态 = `{ assetId, previewUrl }`，生成请求读 blob（现有 `getImageBlob` 路径不变） |
| 变体效果参考 upload kind | blob 存 images，变体替换即删 blob | kind 改 `'asset'`（`{ assetId }` 替代 `uploadKeys`）；上传/选图入库后引用；**替换变体参考不再删资产**（资产归用户，见行为变更 B-3） |
| 效果参考 preset/url kind | 不变 | 不变（preset 指向案例资产同源数据；url 直链保留逃生舱） |
| 生成结果 | putImage(taskId) 扁平存储 | putImage 不变 + 建资产节点入批次文件夹（meta 全量）；任务 meta 增 `assetId` 字段（画廊→库互查 P1） |
| 清空历史 | 连带 deleteImage 删 blob | **只清任务 meta 与画廊，不动资产**（资产删除唯一入口=素材库/回收站） |
| 画廊卡片 | — | P1 增「在素材库中显示」（跳库并定位）；卡片菜单增「删除此图」= 删资产（经回收站）+隐藏卡片 |

送转化（`sendToStudio`）：payload 从 dataUrl 改为**资产引用**——

```ts
// handoff.svelte.ts v2
export interface HandoffPayload {
  assetId: string          // 中间稿资产（生成时已自动入库，此处仅传 id）
  name: string             // 建议名（沿用变体-候选N）
  referenceAssetId?: string // 实验室参考原图的资产 id（若有）
}
```

工作台 `loadFromHandoff` → `getImageBlob(assetId)` → dataUrl → 既有解码管线。dataUrl 中转仅在消费瞬间存在，不再驻留 store（省内存：一张 1024² PNG dataUrl ≈ 1-2MB 字符串，现状每次 handoff 都驻留）。

**「送转化 = 存库 + 选中」的裁决：是。** 生成结果本来就自动入库；送转化的全部增量语义 = 交接选中（切视图+载入）。两者合一后，从画廊删除任务卡不影响已送转化的资产，从素材库删资产后画廊卡显示 imageMissing 同款降级——数据关系清晰。

#### 工作台（StudioView / studio.svelte.ts）

| 项 | 现状 | 重构后 |
|---|---|---|
| 入图（数字油画） | handoff dataUrl / 本地上传，origin: 'handoff'\|'upload' | 空态双 CTA：**从素材库选择**（主）/ 上传（次，入库+选中）；origin 增 `'library'`。`StudioImage` 增 `assetId?`（会话态照旧：解码像素仍是工作台私有派生） |
| 参考原图（叠原图） | 本地上传 / handoff.reference dataUrl | 选图器（或上传入库）+ handoff.referenceAssetId 解析；store 存 `{ assetId, dataUrl }`（dataUrl 为渲染缓存） |
| 送精修 | buildManualEditHandoff 带 referenceDataUrl 烘焙 | `referenceAssetId` 替代 dataUrl（§6 冲突标注） |

#### 手动编辑（EditView / edit.svelte.ts）

- **底图快照来源**：维持 ManualEditHandoff 烘焙（paintingSnapshot 深拷贝像素）——数字油画是「工作台参数的派生中间态」，不属于资产层；素材库只存原料与成品，不存中间态（否则每次调参都产生新资产，库会爆炸）。此为「派生烘焙 / 不可变引用」二分法的直接推论。
- **参考原图**：`referenceAssetId`（替代 referenceDataUrl；§6）。
- **导出 PNG 存库**：导出动作 = 下载 + 入库 `sys-exports`（name：`精修 · <来源摘要> · MM-DD HH:mm.png`，source='edit-export'）。导出成功 toast 提供「在素材库中查看」。

## 3. 设计任务二：转化工作台布局完全重设计

### 3.1 核心作业与高频动线重推（Journey First）

工作台的本质作业：**把一张中间稿调成一份可生产的钻位方案**——在「看得清」与「买得起/做得出来」之间反复权衡（密度↓=钻数↓=成本↓但质感↓）。拆开：

```
载入 → 看全局（这是张什么图，分了几块，多大） → 粗调（全局密度/SS/禁用大区域）
  → 逐块精调（点块 → 密度/类型/颜色；看画布即时重排）        ← 80% 时间在此循环
  → 策略对比（五种排法选一种：看密度均匀性/边缘贴合/总钻数）
  → 终检（叠原图/叠稿核对走样） → 导出（SVG+BOM，答案=共 N 钻）/ 送精修
```

关键观察（判断，依据源码结构 + 上版 IA 用户故事映射，置信度中高）：

1. **循环结构**：「调参数 → 看画布 → 再调」是核心循环。循环的两端（控制 vs 反馈）距离必须最短，且**画布必须在循环全程可见**——参数变了画布没看见等于没调。
2. **对比是模式，不是家具**：五策略对比发生在决策时刻（通常 1-2 次/会话），平时只是「当前是哪个策略」。上版把它做成了常驻大区块（CompareGrid 卡高 ~190px + 区头 + 预览工具行，`CompareGrid.svelte` L204-326），迫使画布让位到 45vh。
3. **答案是常量**：「共 N 钻 + 校验 + 导出」是全程心态锚点（朋友画像的第一问题，上版 IA §1.4 #14），应常驻可见而非滚到页底才见。
4. **预览模式与修复是画布的属性**：叠稿/叠原图/透明度控制的是画布呈现（`previewMode/overlayOpacity`），边界松弛/斥力是响应校验违规的修复动作（`setRelax`）——两者都该长在画布周边，而不是住在 CompareGrid 区头里。

### 3.3 结构诊断：为什么「功能都对、合起来不对」

1. **画布是滚动物件，不是舞台**。桌面主区是 `overflow-y-auto` 长列（来源行 → 画布 45vh → 摘要 → 对比 → 导出，`StudioView.svelte` L107-186）。滚到导出条时画布已离屏——调密度（左栏）看不到画布反馈的窗口期；反之看画布时答案位不可见。核心循环的两端被滚动切断。**这是 Owner 不满意的根因（判断，置信度高）**：三轮视觉迭代都在打磨列内卡片的观感，没有动「列」这个结构。
2. **对比区承担了三种不相干职责**：策略对比 + 预览模式控制 + 修复开关同居 CompareGrid（§3.1 观察 4），区头拥挤且预览控制远离画布。
3. **答案位是流内元素**：状态（N 钻/校验/策略）随滚动消失，违反「State visibility」。
4. **左栏静态频率倒挂残留**：340px 常驻列在「无选中块」时大半是空详情 + 折叠组头（低信息密度占屏）；而高频的密度微调发生在选中态——检查器应为上下文而生，无选中时让位给画布。

| 结构复杂度 | 中（对比覆盖层是新组件） | 高（浮动检查器 + 吸边 + 图标条浮面板，状态多） |
| 移动端可延展性 | ★★★ 胶片带=横滑 chips，同构 | ★ 无成立形态 |

**推荐 A**。决定性论据两条：(1) 高频路径（逐块精调循环）A 全面占优，B 的常驻对比服务的是低频决策且以小图形态存在——「随时能看但看不清」是伪可用；(2) B 的浮动检查器把最高频控件做成了最不稳定容器（遮挡/吸边/开合状态），违反「改一次管一块的放在手边」的上版裁决。B 的合理内核（对比随时可达）由 A 的胶片带 hover 预览 + 常驻「⤢对比」入口吸收。

#### A 的键盘与可达性

- 1-5 切策略（胶片带快捷键，P1）；F=适应；+/−=缩放；Esc=退出对比模式/关弹层。
- 状态条/胶片带/检查器均为 tab 可达；检查器折叠组 aria-expanded；对比覆盖层 focus trap。

## 5. 成功标准（素材库 + 工作台合并）

**主指标（各一）**：

- 素材库：跨模块图片复用率——工作台/编辑从素材库选图（含 handoff 引用）的占比，目标 2 周窗口 ≥80% 的入图会话不再发生「同一张图第二次上传」。[基线=现状 100% 靠重传/handoff；目标值为假设，首发校准]
- 工作台：精调循环深度——每会话块级参数调整次数（density/禁用/覆写），新布局下不降反升（≥基线 110%）且「调整→画布反馈」全程画布可见率 100%（结构性目标，可埋点）。

**支撑指标**：素材库周活打开率（是否成为真入口 vs 死 Tab）；回收站还原率（软删价值验证）；对比模式进入次数/会话（验证「模式非家具」假设）。

**护栏**：三模块管线回归零破坏（现有测试全绿）；1 万钻画布 60fps 不回退；IndexedDB 写入不阻塞生成交互（入库异步化）。

**验证计划**：任务走查 5 条——①新用户：上传→生成→送转化→导出全程不打开素材库也顺畅（素材库不得成为新障碍）；②跨会话复用：昨日生成图今日直接入工作台；③素材库整理：建文件夹/移动/回收站/清空（含引用保护）；④312px 窄屏与 375px 工作台走查；⑤清空历史后素材完好。

## 8. 给 Codex 的议题清单（附立场）

1. **blob 存储复用 vs 新建 store**：资产 blob 继续存既有 `images` store（blobKey 间接引用）vs 新建 `assetBlobs` store 并迁移拷贝。
   立场：**复用 `images`**。迁移零拷贝（存量 taskId/effectref key 原地成资产）、v1 数据回退路径自然；代价是 store 名义上从「生成图缓存」扩义为「blob 仓」——用注释与类型边界弥补。新 store 的唯一收益是语义洁净，不值一次全量 blob 搬迁（IDB 无 move，拷贝有配额风险）。
2. **交接引用化与烘焙边界**：lab→studio handoff 与 ManualEditHandoff.referenceDataUrl 从 dataUrl 载荷改为 assetId 引用（§6 C-1/C-2）。
   立场：**改**，且趁 add-manual-edit-mode 未关改动窗口执行。判据=「派生数据烘焙、不可变资产引用」二分法；Codex 若认为 handoff 应保持自包含（不依赖 assetStore 可用性——如迁移失败场景），可保留 dataUrl 作 fallback 双写一版，但编辑文档内驻留大 dataUrl 的内存代价应有数据支撑再决定。
3. **生成结果自动归档目录策略**：按批次自动建文件夹（本方案）vs 全部平铺进 `生成结果` + 靠元数据过滤/搜索。
   立场：**按批次文件夹**。与画廊分组心智同构（runId）、文件夹需求（Owner 原话「支持文件夹」）在核心数据上即刻成立、无搜索的 P0 也可浏览；代价是「改一次提示词连跑多次」的用户会积 folder——由移动/合并整理（P1 拖拽）解决。平铺方案在 P0（无搜索）不可用。
4. **工作台布局方案 A vs B**（§3.4）。
   立场：**A（舞台+检查器+胶片带+对比模式）**。高频精调循环占优 + 移动端同构；B 的常驻对比列以牺牲画布与检查器稳定性换取「随时可见但看不清」的小图。若 Codex 从代码结构角度发现 CompareGrid 拆分风险大于重排收益，需要给出拆分的具体风险点而非否定方向。
5. **删除语义**：P0 软删（回收站）vs P0 硬删（确认对话框）+ P1 回收站。
   立场：**P0 软删**。实现成本≈硬删（移动指针 vs 删记录+引用检查），误删保护即得；唯一反向论据是「回收站 UI 拖累 P0 范围」——但 P0 回收站可以只是「一个系统文件夹 + 计数徽标 + 清空按钮」，还原 UI 可 P1。
