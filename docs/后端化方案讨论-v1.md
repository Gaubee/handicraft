## 0. 现状盘点（迁移的起点）

- 前端：Vite+Svelte5+TS strict；**确定性引擎（分块/排布/校验/导出）是纯 TS 零依赖模块**——这是最大资产
- 数据：IndexedDB（图/资产）+ localStorage（任务/设置）+ 四族文件格式（.gemproj/.gemdoc/.gemtpl/.gemgen）
- 生成：浏览器 BYOK 直连 gpt-image（key 仅存浏览器，CORS 靠中转站）
- 部署：GitHub Pages（workflow 构建）+ handicraft.gaubee.com，CI 已通
- 客户参照系：ComfyUI+GPU 识别 → 有机排布 → 四层 SVG/编号图/色卡 XLSX/印刷 TIF（分析进行中，vision 双代理报告将并入）

## 1. 目标架构（提议）

```
                    handicraft.gaubee.com
                           │
                    ┌──────▼──────┐
                    │  反向代理     │（VPS 上 nginx/1Panel/caddy）
                    └──────┬──────┘
              ┌────────────┼────────────┐
        ┌─────▼─────┐ ┌────▼─────┐ ┌────▼──────────┐
        │ Web 静态壳  │ │ API 服务  │ │ Worker(s)     │
        │ (Svelte 构建)│ │ Node/TS  │ │ Python(GPU)   │
        └────────────┘ │ Fastify/  │ │ ComfyUI 对接/  │
                       │ Hono      │ │ 识别管线(后期) │
                       └────┬─────┘ └───────────────┘
                            │
                    ┌───────▼────────┐
                    │ SQLite + 对象存储 │（单机起步：文件系统 + SQLite）
                    └────────────────┘
```

**核心提议——双语言分工**：
- **Node/TS 承载 API 与业务编排**：我们的引擎是纯 TS——**原样在后端复用**（大图排钻、校验、SVG/BOM/PNG 生成全部服务端跑，浏览器只做预览交互）。零重写成本，这是选 Node 做主服务的第一理由
- **Python 承载 AI/算法面**（Phase 2）：ComfyUI 生态、检测/分割模型、客户管线的对齐与替代——py 生态不可替代，且客户工作流本身就是 Python 系

## 2. 分阶段路线（提议）

**Phase 1 · 最小后端化（先立骨架）**
1. `services/api`（Node/TS，Fastify 或 Hono）：
   - 生成代理：gpt-image 调用移到服务端（终结 CORS/中转站依赖；密钥服务端集中——语义变化见 §4-③）
   - 任务与资产持久化：IndexedDB/localStorage 的服务端对应物（SQLite + 文件存储），文件格式继续作为导入导出交换格式（旧档全兼容）
   - 引擎服务化：重计算（排钻/导出）API 化
2. 前端改「瘦客户端」：fetch 替代本地 IDB/localStorage 读写（渐进替换，UI 不动）
3. 部署迁移：Docker Compose（web+api+db）上你的服务器；handicraft.gaubee.com 解析从 GitHub Pages 切到 VPS；GitHub 仓库保留（CI 改为构建镜像/交付物）；gh-pages 可留作引导页或 301

**Phase 2 · 客户管线对齐（GPU 工作面）**
- Python worker + ComfyUI 对接（或吸收客户工作流逻辑自研）：原图→识别→分色→**有机排布**→四层 SVG/编号图/色卡 XLSX 生产包
- 客户分析报告（vision 进行中）落地后细化：哪些节点直接复用 ComfyUI、哪些用自研替代（我们引擎的确定性排布 vs 客户的识别驱动有机排布，可两条路线并存）
- GPU 拓扑：客户 VM 常驻 worker（远端）vs 自有 GPU vs 云 GPU——待定

**Phase 3 · 生产化**（按需）：多用户/多客户、任务队列与优先级、预览缓存、计费/用量……

## 3. 仓库与工程形态（提议）

- Monorepo：`rhinestone-studio/`（前端，engine 保留原地）+ `services/api/`（Node）+ `services/worker-py/`（后期）+ `docs/`
- engine 不搬家：前端与 api 共同依赖（workspace 包 `@handicraft/engine` 双消费），单仓内引用不发包
- CI：GitHub Actions 构建前端静态产物 + api Docker 镜像

## 4. 决策点（本讨论稿的核心，待你逐条拍板）

| # | 问题 | 我的建议 | 备选 |
|---|---|---|---|
| ① | **部署到哪** | 你的 VPS（我在你机器上看到 1Panel 痕迹——Docker Compose 最顺） | 云容器平台/家宽自托管/暂用云开发环境 |
| ② | **用户体系** | 先单用户（你）+ 简单口令，不做多租户——客户场景后期再说 | 直接多用户（决定 DB 与 auth 复杂度） |
| ③ | **BYOK 语义** | 密钥移服务端环境变量（集中管理，不再依赖浏览器 localStorage） | 保持每用户 BYOK（后期多租户需要） |
| ④ | **GPU 跑在哪** | Phase 2 再定；若客户 VM 可常驻，先对接它（省 GPU 成本，客户已给账号） | 自购 GPU/云 GPU（按时租） |
| ⑤ | **Phase 1 范围** | 只做：生成代理+存储+引擎 API+部署迁移（不动 UI 不动产品功能） | 连同客户管线能力一起冲（更大更慢） |
| ⑥ | **域名切换策略** | VPS 就绪后 handicraft.gaubee.com 平滑切（Pages 保留兜底一周） | 直接硬切 |

## 5. 风险与代价（诚实面）

- 前端「离线可用」能力让渡（现在 IDB 本地全量可用；后端化后依赖服务）——可保留文件导入导出作离线兜底
- 运维面新增：服务器、TLS、备份（SQLite+文件目录的定期备份即可起步）
- 开发节奏：Phase 1 约一个常规 change 周期（含双端测试与迁移验收）；产品功能（设计师/实验室）在此期间冻结还是并行，待你定
- GitHub Pages 现有 CI 的角色降级（只留引导页/发布归档）
